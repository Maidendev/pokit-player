# PokitPlayer — Open-Source Licence Audit (Player Binary)

**Product:** PokitPlayer 1.2.7 (Electron desktop application)
**Owner:** Maiden Media Solutions INC.
**Prepared:** 2026-09-03
**Scope:** the distributed player binary only — Windows NSIS/portable, macOS DMG/ZIP,
Linux AppImage/deb.
**Companion files:**
`PLAYER-COMPONENTS.md` (generated inventory) · `pokitplayer.cdx.json` (CycloneDX SBOM)

This is an engineering findings document prepared for counsel. It states what is in the
build and how it got there. It does not offer a legal conclusion on any of it.

---

## 1. Bottom line

**There is something in the flagged buckets. Two things, and one of them blocks release.**

| # | Finding | Severity |
|---|---|---|
| 1 | The macOS FFmpeg binary is built `--enable-nonfree`. FFmpeg's own position is that such a build **cannot be redistributed at all**, under any licence. It is in the shipped Mac app today. | **Blocking** |
| 2 | Every bundled `ffmpeg` and `ffprobe` binary, on every platform, is **GPL-3.0-or-later** — not LGPL. Six components. | **High** |
| 3 | `ffprobe-static` declares **MIT** to npm while shipping GPL-3 binaries. Any package-manager-only scan reports this component as clean. | **High** (method risk) |
| 4 | The macOS build ships an **arm64** FFmpeg inside the Intel DMG, and an **x86_64** ffprobe inside the arm64 app. | Functional bug |

There is **no AGPL, no SSPL, and no non-commercial or research-only licence** anywhere in
the player. Every one of the 39 npm packages is permissive (MIT, ISC, BSD, Apache-2.0,
Python-2.0, Blue Oak). **Nothing has been modified** — no patched dependency, no vendored
third-party source in `src/`.

So the exposure is narrow and concentrated. It is entirely in the two media binaries, and
it is fixable. Section 5 sets out the options.

## 2. The four questions, answered

### Every third-party component, with version and licence

`PLAYER-COMPONENTS.md`, generated by `npm run oss:inventory`. 49 components ship to a
customer machine: 39 npm packages and 10 native binaries/runtimes. `pokitplayer.cdx.json`
is the same data as CycloneDX 1.5 for whatever tooling diligence uses.

Note the report is **not** a bare `npm sbom`. A package-manager-only list misses this build
in two specific ways, both material:

- it reports `ffprobe-static` as MIT, which is the licence of about twenty lines of
  path-resolving JavaScript, not of the GPL-3 FFmpeg binaries the package vendors; and
- it cannot see the `ffmpeg` binary at all, because `ffmpeg-static` **downloads** it during
  `npm install` rather than shipping it in the package.

The native layer is therefore hand-verified and kept in
`scripts/oss-native-components.json`, with the evidence recorded alongside each entry.

### How each one is linked

| Linkage | Components | Why it matters |
|---|---|---|
| Separate process | `ffmpeg`, `ffprobe` (all platforms) | Launched via `child_process.spawn` / `execFile`, communicated with over stdio only. **No linking of any kind** — not static, not dynamic. This is the most favourable posture available for a GPL dependency, and it was already the architecture; nothing needs to change to preserve it. |
| Dynamic | Electron's internal `libffmpeg` | Separate shared library (`.so`/`.dylib`/`.dll`), LGPL-2.1-or-later, replaceable by the user. |
| Runtime-bundled | Electron, Chromium, Node.js | The application runtime. MIT / BSD-3-Clause. |
| `require()` | all 39 npm packages | Pure JavaScript into the Electron main process. No compiled native extensions. |

The call sites, if counsel wants to see them: `src/stream-decoder.js:152`,
`src/transcoder.js:219,532,681`, `src/loudness.js:118`, `src/captions.js:448`,
`src/inspector.js:82,603`.

**The separate-process boundary is the whole argument here, and it is worth being precise
about what it does and does not do.** It goes to whether the *application* becomes a
derivative work of the GPL binary. It does nothing at all about the separate obligation
that attaches to *distributing the GPL binary itself* inside our installer — that
obligation exists regardless of how cleanly the process boundary is drawn, and it is the
one that needs a decision.

### Anything modified rather than used as-is

**Nothing.** No patched dependency, no forked package, no third-party source copied into
`src/`. Every component is consumed at its published version. The `modified` column in the
inventory is `no` across all 49 rows.

### Anything under GPL, AGPL, SSPL, non-commercial or research-only

- **GPL-3.0-or-later:** 6 components — the `ffmpeg` and `ffprobe` binaries on every
  platform, plus the `ffmpeg-static` npm wrapper, which correctly declares itself GPL.
- **Non-distributable:** 1 component — the macOS arm64 FFmpeg, `--enable-nonfree`.
- **AGPL / SSPL / non-commercial / research-only:** **none.**
- **LGPL-2.1-or-later:** 1 component — Electron's internal `libffmpeg`, dynamically
  linked, which is the arrangement LGPL is written to permit.

## 3. FFmpeg — the specific answer

The instinct in the request was right, and it is worth confirming precisely: **a stock
FFmpeg build is LGPL, and `--enable-gpl` or a GPL-licensed encoder makes the whole binary
GPL.** That is exactly what has happened here, on every platform.

FFmpeg compiles its `configure` line into the executable, so this is not inference — the
flags below were read out of the shipped binaries with
`strings -a <binary> | grep -- --enable-gpl`. Re-runnable at any time via
`npm run oss:verify`.

| Platform | Binary | Version | Licence | Decisive flags |
|---|---|---|---|---|
| Windows x64 | ffmpeg | 6.1.1 (gyan.dev) | GPL-3.0-or-later | `--enable-gpl --enable-version3 --enable-libx264 --enable-libx265` |
| macOS x64 | ffmpeg | 6.1.1 (Tessus) | GPL-3.0-or-later | `--enable-gpl --enable-version3 --enable-libx264 --enable-libx265` |
| **macOS arm64** | **ffmpeg** | **6.0** | **GPL-3 + `--enable-nonfree`** | **`--enable-nonfree` — not redistributable** |
| Linux x64 | ffmpeg | 7.0.2 (John Van Sickle) | GPL-3.0-or-later | `--enable-gpl --enable-version3 --enable-libx264 --enable-libx265` |
| All platforms | ffprobe | 4.0.2 / 4.4 | GPL-3.0-or-later | `--enable-gpl --enable-version3 --enable-libx264 --enable-libx265` |

Two flags do the work. `--enable-gpl` relicenses the binary from LGPL to GPL.
`--enable-version3` moves it from GPL-2 to **GPL-3**, which carries additional terms
(notably the installation-information provisions) that a GPL-2 analysis would miss. Both
are present in all six.

Even if `--enable-gpl` were removed, these builds would still be GPL: **x264, x265, Xvid,
Rubber Band, vid.stab and frei0r are each independently GPL**, and FFmpeg's `configure`
refuses to link any of them without `--enable-gpl`. Removing the flag means removing the
libraries.

### Where the binaries come from

`ffmpeg-static@5.3.0` does not ship a binary. Its `install.js` **downloads one at
`npm install` time, chosen by the host platform and architecture**, from release tag
`b6.1.1`. Three consequences worth naming:

1. **Nobody chose these builds.** They are third-party community builds — gyan.dev,
   Tessus, John Van Sickle, and for arm64 an unattributed build. The `--enable-nonfree`
   flag arrived without anyone deciding to accept it.
2. **The build machine determines what ships.** CI runs on `macos-latest`, an arm64
   runner, so `npm install` fetches the arm64 binary — and electron-builder then packages
   that same arm64 binary into **both** the arm64 and the x64 DMG. The Intel Mac build
   ships an executable that cannot run on an Intel Mac, and both ship the non-distributable
   one.
3. **The pin is soft.** `"ffmpeg-static": "^5.3.0"` combined with a download step means a
   fresh `npm install` on a different machine can produce a differently-licensed binary
   without any change to the repository.

### One complication for remediation

`src/stream-decoder.js:93` encodes with **`-c:v libx264`**. This is not an incidental
feature — it is the core playback pipeline, transcoding ProRes/DNx to fMP4 for Media Source
Extensions. `src/transcoder.js` uses libx264 in two more places.

So "just switch to an LGPL FFmpeg build" removes x264 and breaks primary playback. The
swap needs a replacement encoder, which is real work rather than a flag change. Section 5
covers it.

### Adjacent, and not an open-source question

Electron's default build enables proprietary codecs (H.264 / AAC), and the player decodes
H.264, AAC and HEVC. Those carry **patent** licensing considerations — Via LA, Access
Advance — that are entirely separate from copyright licensing and unaffected by anything in
this document. Flagged only so it is not assumed the OSS audit covered it. It did not.

## 4. What is explicitly clean

So the picture is not one-sided:

- **All 39 npm packages are permissive.** MIT, ISC, BSD-2/3-Clause, Apache-2.0,
  Python-2.0, Blue Oak 1.0.0. No copyleft anywhere in the JavaScript tree.
- **No AGPL and no SSPL** — the network-triggered licences — anywhere in the player.
- **No non-commercial or research-only licence** anywhere in the player.
- **Nothing modified.** No patches to unwind, no fork to maintain, no obligation to
  publish changes.
- **No linking against GPL code.** The media binaries are separate processes and always
  have been.
- **Two licences resolved by hand** where npm published no metadata: `async@0.2.10` (MIT)
  and `parse-cache-control@1.0.1` (BSD-3-Clause). Both read off the `LICENSE` file in the
  installed package, not assumed. Neither is copyleft.

## 5. Options

Engineering options with honest costs, for counsel to choose between. Roughly ascending
order of effort.

### Option A — Fix the blocking item only, keep GPL

Pin FFmpeg to a known GPL-3 build that is **not** `--enable-nonfree` on every platform, and
build each Mac architecture on its own runner so the right binary ships. Then comply with
GPL-3 for the redistributed binaries: ship the licence text, publish the corresponding
source (or a written offer), and satisfy the GPL-3 installation-information terms.

- **Effort:** 1–2 days of build work.
- **Removes:** the non-distributable binary. Keeps the GPL-3 obligation, deliberately.
- **Trade-off:** GPL-3 in a commercially distributed product is a posture some acquirers
  and enterprise customers question. It is a decision to make consciously rather than
  inherit, and it is counsel's call, not engineering's.

### Option B — Move to LGPL FFmpeg, replace the encoder

Build or source LGPL FFmpeg (no `--enable-gpl`, no x264/x265/Xvid/Rubber Band/vid.stab)
and replace the libx264 playback encoder. Viable replacements, all LGPL-compatible:

- **Hardware encoders** — `h264_videotoolbox` (macOS), `h264_nvenc` / `h264_qsv` /
  `h264_amf` (Windows). Fastest path, and likely *faster* than libx264 ultrafast for this
  workload. Needs a software fallback.
- **`libvpx` VP9 into fMP4** — BSD-licensed, decodes natively in Chromium/MSE. No hardware
  dependency; slower to encode.
- **`libopenh264`** — BSD, from Cisco, but its patent-royalty arrangement is specific to
  Cisco's own distributed binary and would need review before relying on it.

- **Effort:** roughly the week the request anticipated — one week for the encoder swap and
  playback validation across the format matrix, plus the FFmpeg build pipeline.
- **Removes:** GPL entirely. Leaves LGPL, satisfied by the existing separate-process
  architecture without further work.

### Option C — Build FFmpeg ourselves, LGPL, minimal

Same licence outcome as B, plus control over exactly what is in the binary and a much
smaller installer (the current builds carry a great deal we never invoke — Bluray, AviSynth,
ZeroMQ, GME, OpenMPT). Also resolves the ffprobe 4.0.2-vs-ffmpeg 6.1.1 version mismatch
already recorded in `PINNED.md`.

- **Effort:** 2–3 weeks including CI for three platforms.
- **Worth it if** the player is a long-lived product; overkill if the goal is only to clear
  diligence.

### Recommendation

**Option A now, Option B before any acquirer's technical diligence.** The `--enable-nonfree`
binary should not be in a shipped artefact for another day, and that fix is a day or two of
build work with no product risk. The GPL-to-LGPL move is the one that actually changes the
company's position, and it is a week — cheap now, and exactly the kind of thing that gets
expensive once there are customers on the current build.

### One small item either way

`src/main.js:306` — the About dialog reads *"Built with Electron + ffmpeg.\n\nMIT
License"*. That is inaccurate today regardless of which option is chosen. The correct
replacement depends on the licensing decision, so it is deliberately left unchanged here
rather than guessed at. It should be corrected as part of whichever option is taken, along
with shipping the required licence texts in the installer.

## 6. The non-urgent half — scoping note

The second half of the request (server-side stack, model weights, training data) **cannot
be answered from this repository.** `Maidendev/pokit-player` contains the player and
nothing else: no server code, no model artefacts, no training or fine-tuning pipeline, no
dataset references. I looked; there is nothing here to report on, and reporting "clean"
would be misleading rather than reassuring.

That work needs the repositories to be named and made accessible. When they are, the same
generator extends to cover them — the distinction the request asked for is already modelled
in the schema:

- **`shipsToCustomer: true|false`** — separates distributed code from server-only code.
  This is the AGPL/SSPL line, and it is the one that matters: those licences trigger on
  serving software over a network, which is precisely what a server-side component does.
  Worth checking early for the usual suspects — MongoDB, Elasticsearch, Redis (post-2024),
  Grafana, MinIO — all of which changed licences in the last few years, several to SSPL or
  AGPL.
- **Model weights and training data** need their own manifest rather than a code SBOM.
  Licence, provenance and commercial-use permission are per-model facts that live in model
  cards, not in a package manager. The request's instinct is right that this is the harder
  problem — several widely-used open-weight models carry research-only or
  acceptable-use restrictions that are far more painful to unwind than a library swap,
  because a model that has been fine-tuned on restricted weights may carry the restriction
  forward into the derived weights.

Happy to run both as soon as the repositories are pointed at me.

## 7. How to reproduce any of this

```bash
npm install
npm run oss:inventory   # regenerate the inventory and the CycloneDX SBOM
npm run oss:check       # CI gate — exits 1 if any copyleft/non-distributable component is present
npm run oss:verify      # re-read the actual binaries and print their GPL/nonfree flags
```

`oss:verify` output as of 2026-09-03 — seven of seven binaries, independently confirmed:

```
ffmpeg-static (host platform)     GPL v3 libx264 libx265 libxvid librubberband libvidstab frei0r
ffprobe-static darwin/arm64       GPL v3 libx264 libx265 libxvid librubberband libvidstab
ffprobe-static darwin/x64         GPL v3 libx264 libx265 libxvid libvidstab
ffprobe-static linux/ia32         GPL v3 libx264 libx265 libxvid librubberband libvidstab frei0r
ffprobe-static linux/x64          GPL v3 libx264 libx265 libxvid librubberband libvidstab frei0r
ffprobe-static win32/ia32         GPL v3 libx264 libx265 libxvid libvidstab
ffprobe-static win32/x64          GPL v3 libx264 libx265 libxvid libvidstab

7 of 7 binaries carry GPL or nonfree build flags.
```

`oss:check` is wired to exit non-zero, so it can be added to CI to prevent a new copyleft
component from arriving unnoticed. It is deliberately **not** in the build job yet — it
would fail the build today, correctly, and that decision belongs with the licensing
decision.
